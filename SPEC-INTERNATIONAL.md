## 0. Guiding principles

These constraints come first; everything below must respect them.

1. **Client-side only.** Nothing in this spec introduces a server, a build pipeline that requires a server, or any runtime network call. Every new tool runs in the browser. Anything that cannot run in the browser is out of scope, full stop.
2. **No third-party requests.** No CDN, no fonts, no analytics, no telemetry. Vendored dependencies only. New deps must be small, MIT/BSD/Apache-2-licensed, and copy-pasteable as a single file.
3. **No fingerprinting.** Locale comes from `navigator.language` and `localStorage` only. Country is never inferred (no IP geolocation, no `Intl.DateTimeFormat().resolvedOptions().timeZone`-based country guessing). The same site is served to everyone; users opt in to a locale.
4. **No PII validators.** See [§7 Tensions](#7-tensions-and-non-goals). Commercial identifiers (IBAN, VAT, BIC, GS1) are fine. National identity numbers are not.
5. **No compliance theater.** No cookie-banner builders, no DPA templates, no "GDPR auditor" tools. The site is a technical toolbox, not a legal product.
6. **Translation quality > translation breadth.** A new locale ships only after a native reviewer has signed off on the strings that appear on screen. Machine-quality drafts are fine as scaffolding; they are not fine as a shipped locale unless explicitly labeled "machine-translated, awaiting review" in the UI.
7. **Reversibility.** Every workstream below should be revertable by deleting files. No global rewrites, no architectural commitments that lock the project in.

### 1.3 Translation methodology — "multiple passes"

The bar this project should hold: **a native speaker who works in tech can read the UI without wincing.**

Procedure for each new locale:

1. **Pass 1 — machine draft.** Run an LLM (or DeepL for European locales, which is genuinely strong on EU languages) against the `en` column of `strings.csv`. Mark every cell `machine` in the per-locale `_status` column.
2. **Pass 2 — glossary lock.** Before reviewing prose strings, lock the translations of the core technical glossary (see [§1.7](#17-core-glossary-translation-targets)) for that locale. Every occurrence of "encrypt", "decrypt", "key", "passphrase", etc. must use the same target term across the file. The CSV makes this a global find-and-replace; do it in one pass.
3. **Pass 3 — native review.** A native speaker who reads code goes through the CSV row by row. They flip `_status` from `machine` to `reviewed` once they're satisfied. They are explicitly allowed to mark cells `awkward` or `needs-context` and leave them for the maintainer to revisit.
4. **Pass 4 — in-context review.** Build the variant (`scripts/build-i18n-variants.js`), open `/<locale>/index.html`, click through every tool. Strings that read fine in a spreadsheet sometimes read wrong in a button. Note overflows, truncations, line-wrap problems, mismatched case (English title case doesn't transfer to most languages).
5. **Pass 5 — RTL pass (RTL locales only).** Same as Pass 4 but in the RTL build, with eyes on icon directionality (arrows, chevrons, progress indicators), tabular alignment, and any place CSS uses `left`/`right` instead of `inline-start`/`inline-end`.
6. **Pass 6 — date/number/plural smoke test.** Generate a UUID v7, decrypt a file, decode a cron expression. Confirm dates render in the locale's conventional order, decimal separators are correct, and pluralized counts agree.
7. **Sign-off.** All cells `reviewed` (or explicitly `n/a` for strings that don't apply, e.g., English-only acronyms). Add the locale to `VARIANTS` in `build-i18n-variants.js`, to the `hreflang` block in `index.html`, and to the language picker.

Anything short of this ships with a visible banner: *"This locale is machine-translated and awaiting native review — corrections welcome at [link]."*

Remaining §1.5 work (deferred to a future slice): `Intl.PluralRules` integration for `{n} shares` / `{n} matches`-style strings (needs the CSV schema extension below), `Intl.ListFormat` for Shamir / multi-recipient phrasing, and `Intl.Collator` for any palette sort that lands with §1.6.

The browser's `Intl` namespace handles this without dependencies. Touch points:

- **`Intl.NumberFormat`** — Decimal commas in French/German/Italian/Spanish/Polish/etc. Affects: PBKDF2 derivation time display, file sizes, "5 minutes ago" thresholds, color converter percentages, CIDR host counts, hash collision probabilities.
- **`Intl.DateTimeFormat`** — Unix timestamp converter (already shows UTC + local + relative; add locale-formatted absolute). Cron decoder next-fire times. TLS / PGP key validity windows.
- **`Intl.RelativeTimeFormat`** — Replace the hand-rolled "5 minutes ago" with `RelativeTimeFormat`. Handles Polish/Russian/Arabic plurals correctly.
- **`Intl.PluralRules`** — Strings like `"{n} shares"`, `"{n} matches"`, `"{n} bytes"`. Use a small helper:

  ```js
  function plural(locale, n, forms) {
    const rule = new Intl.PluralRules(locale).select(n);
    return (forms[rule] || forms.other).replace('{n}', n);
  }
  // forms = { one: '{n} share', few: '{n} shares', many: '{n} shares', other: '{n} shares' }
  ```

  Strings file gets one entry per plural category, not one entry per language hard-coded. The CSV schema needs a small extension: a `key.plural.one`, `key.plural.few`, `key.plural.many`, `key.plural.other` convention. Backwards compatible — existing entries are treated as `other`.

- **`Intl.ListFormat`** — "share A, share B, and share C" / "share A, share B y share C". Surfaces in Shamir, QR multi-part output, multi-recipient encryption.
- **`Intl.Collator`** — If the command palette ever sorts strings alphabetically per locale (German ß, Swedish å, Czech č all sort differently), use `Collator`. Not urgent.

**Translation pitfalls observed during these passes** (notes for the maintainer):

- **Spanish "encriptar" vs "cifrar".** Both are widely used; cryptographers prefer "cifrar". Lock one project-wide. I recommend `cifrar` (the academic / industry-standard term in Spain and most LatAm cryptography literature) but include `encriptar` in the palette synonyms.
- **French "chiffrer" vs "crypter".** `chiffrer` is correct; `crypter` is a frequent calque from English and is technically wrong (in French cryptographic literature "crypter" means *to encode in an unknown cipher*). Use `chiffrer` in UI strings, include `crypter` as a palette synonym only.
- **Portuguese "criptografar" vs "cifrar".** Both used; in pt-BR `criptografar` is more common; in pt-PT `cifrar` is more common. Pick per-locale.
- **German "verschlüsseln" vs "chiffrieren".** Use `verschlüsseln` (modern); `chiffrieren` is archaic.
- **Russian/Ukrainian "ключ".** Same word as "key" in any sense (door key, musical key). Always pair with the modifier (открытый/закрытый, відкритий/закритий) in UI labels, never alone.
- **Polish verb aspect.** Polish has perfective/imperfective verb pairs. Button labels should use the perfective (`Zaszyfrować` — "to encrypt [completely]"), not imperfective (`Szyfrować` — "to be encrypting"). This is a frequent machine-translation error.
- **Arabic gendered verbs.** Imperative button labels in Arabic carry implicit gender. Use the masculine singular form by convention (this is the standard for software UI in Arabic).
- **Japanese "暗号化" vs "暗号化する".** Use the noun form (`暗号化`) for menu labels, and the verb form (`暗号化する`) only inside sentences. Buttons are typically the noun.
- **Chinese "密钥" vs "秘钥".** Both appear in the wild; `密钥` is correct and standard. `秘钥` is a common typo / non-standard variant. Audit `zh-CN` strings for this — it's easy to slip through.
- **Indonesian "berkas" vs "file".** `berkas` is the official Indonesian word but `file` is far more common in tech contexts. Pick `file` for consistency with how Indonesian developers actually speak about software. (Reverse argument: `berkas` is more accessible to non-technical users. Native reviewer to decide.)
- **Turkish vowel harmony.** Suffixes attached to dynamic content (e.g., `{filename}'i indir`) need to obey vowel harmony, which can't be done with simple string interpolation. Prefer rewording (`İndir: {filename}`) over interpolated suffixes.

These notes are explicitly the kind of thing that takes multiple passes — Pass 1 (machine) will get every one of them wrong; Pass 3 (native review) is where they get caught.

### 1.8 Per-locale CSS / typography checklist

- **Latin-script locales:** existing fonts sufficient (system stack).
- **Cyrillic (`ru`, `uk`):** confirm system fonts on macOS, Windows, and Linux cover Cyrillic glyphs at all weights. They do.
- **Arabic (`ar`):** RTL pass + line-height bump (Arabic glyphs sit lower). Avoid italics — Arabic doesn't italicize.
- **CJK (`zh`, `ja`, `ko`):** `word-break: keep-all`, slight line-height bump. Avoid all-caps styling.
- **Indic (`hi`, `bn`, `ta`):** confirm conjunct rendering. macOS and Android handle this well; older Windows fonts can break Bengali ligatures. No fix in CSS — note it in the README.
- **Vietnamese (`vi`):** diacritics stack tall; line-height bump.

## 2. New tools — Europe-resonant additions

Each tool below follows the existing project pattern: pure browser code, zero network, vendored deps only, ASCII-armored or hex output where applicable, constant-time comparisons where they matter.

### 2.1 IBAN validator / generator — **✅ shipped (draft 2)**

**Why:** Every European has typed an IBAN wrong. The tool gives instant feedback on a string that is otherwise opaque.

**Status notes (draft 2):** Landed as the `iban` tool with full English, French, and German UI strings (banking terms locked against the §1.7 glossary). zh-CN and hi have machine-quality drafts pending native review. Country table covers ~80 IBAN-issuing jurisdictions; BBAN sub-fields surfaced where the registry defines them. Generator uses `crypto.getRandomValues` for the BBAN and is labeled "For test data only." Functional tests cover the canonical ECBS example (`DE89 3704 0044 0532 0130 00`), a flipped-digit negative case, and a generator → validator round-trip.

**Spec:**
- Input: a string. Tolerate spaces, dashes, lowercase.
- Validate:
  1. Strip non-alphanumerics, uppercase.
  2. First two chars are an ISO 3166-1 alpha-2 country code with a known IBAN length (table of ~80 countries, ship inline).
  3. Total length matches that country's expected length.
  4. MOD-97 checksum: rearrange `CCKK BBAN` → `BBAN CCKK`, map letters A-Z → 10-35, compute the resulting integer modulo 97, expect 1.
- Output:
  - Pass/fail with reason.
  - Country, bank code, account number, branch code parsed from the BBAN per the country's structure (these subfields vary; ship a per-country regex/structure table).
  - Pretty-printed form (groups of 4).
- Generator side: produce a *valid* IBAN for a given country and BBAN (fill in the two checksum digits using MOD-97). Useful for test data. Label it clearly: **"For test data. Do not use for real transactions."**

**Dependencies:** none. Hand-written, ~120 lines.

**Security notes:** IBANs are commercial identifiers, not PII in any meaningful sense, but the tool should still process input only locally. Pasted IBANs should never appear in the URL, in `localStorage`, or in `document.title`.

### 2.2 BIC / SWIFT code checker — **✅ shipped (draft 2)**

**Why:** Companion to IBAN. ISO 9362 format check.

**Status notes (draft 2):** Landed as the `bic` tool. Validates 8- and 11-character forms, decodes bank / country / location / branch, cross-checks the country segment against the IBAN country table, and flags conventional markers (`0`-terminated → test BIC; `1`-terminated → passive participant; branch `XXX` → primary). en/fr/de translations reviewed against standard banking terminology; zh-CN/hi are machine-quality drafts.

**Spec:**
- Format: `BBBB CC LL [XXX]` — 4 bank, 2 country (ISO 3166-1 alpha-2), 2 location, optional 3 branch.
- Validate length (8 or 11), uppercase, alphanumeric, valid country code, location code rules (second character `0` = test BIC, etc.).
- No checksum (BIC has no checksum), but expose the parsed components and flag test BICs (location code ends in `0`).

**Dependencies:** none.

### 2.3 EU VAT number validator (offline) — **✅ shipped (draft 3)**

**Why:** Catches 90% of typos without ever touching VIES.

**Status notes (draft 3):** Landed as the `vat` tool. Format check for all 27 EU member states + GB, NO, CH, XI (Northern Ireland). Checksum implemented for AT, BE, DE, DK, EE, EL, ES (CIF only), FI, FR, HR, HU, IT, LU, MT, PL, PT, SE, SI, SK, CH, NO (≈ 70% of supported set). Countries without a published or stable algorithm (BG, CY, CZ, GB legacy, IE, LT, LV, NL post-2020, RO, XI) report "format only" without claiming more. ES support is intentionally limited to the CIF subset; individual NIF (`12345678Z`-style) and NIE (`X1234567Z`-style) inputs are explicitly rejected with a message pointing at the spec, satisfying the §7.1 tension constraint. en/fr/de translations locked against standard tax terminology (German `USt-IdNr.`, French `TVA`); zh-CN/hi are machine-quality drafts. Functional tests cover real public VAT numbers from DE/FR/IT (Ferrero `IT00159560366`), the NL "format-only" path, the ES NIF rejection, and a DE flipped-digit negative case.

**Spec:**
- Per-country format and checksum table for all 27 EU member states + GB, NO, CH (close enough to ship together).
- Each country has a different algorithm:
  - DE: 9 digits, weighted checksum.
  - FR: 2-char prefix + 9 digits, MOD-97 derived from the SIREN.
  - IT: 11 digits, Luhn-style checksum.
  - ES: 1 letter + 7 digits + 1 letter/digit, several sub-formats (NIF, NIE, CIF).
  - NL: 9 digits + B + 2 digits, no checksum.
  - PL: 10 digits, weighted checksum.
  - etc.
- Output: pass/fail per the format and (where one exists) per the checksum, plus a clearly-labeled "this is a syntactic check — to verify the VAT number is actively registered, use VIES at the EU Commission's website" disclaimer with a link out.

**Dependencies:** none. ~300 lines of country-specific code.

**Tension flag:** ES NIF/NIE overlap with personal tax IDs. **Validate VAT formats only**, never NIF/NIE for individuals. The CIF (corporate) format is fine. This is one of the rare cases where the line between "commercial identifier" and "PII" is fuzzy — when in doubt, omit the country.

### 2.4 SEPA XML inspector (pain.001 / camt.053 / pain.008) — **🟡 pain.001 + camt.053 shipped (draft 16); pain.008 inherits the pain.001 renderer**

**Status notes (draft 16):** Landed as the `sepa` tool. The parser is namespace-blind — it walks ISO 20022 XML by `localName` only, so the same code handles `pain.001.001.03`, `pain.001.001.09`, `camt.053.001.02`, `camt.053.001.08`, and any other minor revision without per-version branching.

- **pain.001 + pain.008**: header row (MsgId, CreDtTm, InitgPty, NbOfTxs, CtrlSum) + per-`PmtInf` debtor account/IBAN/BIC, then per-transaction (`CdtTrfTxInf` / `DrctDbtTxInf`) end-to-end ID, amount + currency (from `Amt/InstdAmt`'s `Ccy` attribute), debtor + creditor names with their IBANs in parens, remittance info.
- **camt.053**: statement ID, account IBAN, FrToDt window, every `<Bal>` (opening `OPBD` and closing `CLBD` labeled explicitly via the existing strings table; other balance-type codes fall through with their raw 4-letter code), then per-`Ntry` booking date, amount, credit/debit indicator.
- **IBAN cross-check**: every `<IBAN>` element anywhere in the document is run through the existing `ibanValidate()` (the same MOD-97 implementation that powers the IBAN tool). When all checksums pass, a single confirmation row is rendered (`IBAN MOD-97 valid (N)`); on a failure, each bad IBAN gets its own warning row.
- **Unrecognized roots**: a `<Document>` whose first child isn't one of the three known wrappers still renders the header (with the unknown local name as the document type) and then emits a `sepa.warn.unknownDoc` warning rather than refusing the file outright.

UI: a single textarea + Parse button, mirrors the existing IBAN / BIC / VAT layout. No vendored deps — `DOMParser` only. ~200 lines of parser + render JS, ~12 new strings × 5 locales (en + fr + de reviewed against standard banking terminology; zh-CN + hi are machine-quality drafts per the project pattern). 5 SEO prose keys (`tool.sepa.{title,metaDescription,about.{what,how,why}}`) en-only per the existing Phase 7 carve-out.

Four new Playwright cases:

1. pain.001 — parses headers, transactions, both IBANs, and renders `100.00 EUR` + `Invoice 2024-001`.
2. camt.053 — parses statement ID, opening / closing balance, entry amounts.
3. Flipping the last digit of the debtor IBAN — surfaces a MOD-97 warning row with the bad IBAN inline.
4. Non-ISO-20022 XML (`<foo><bar/></foo>`) — reports `No <Document> root element`.

Full Playwright suite: 227 passed. Tool count 42 → 43; JSON-LD `featureList_count`, JSON-LD description, meta description, og:description, twitter:description, and README all updated.

**What's not in this slice:** XAdES-signed SEPA files (the embedded `<ds:Signature>` inside pain.001 production files is parsed *around* by the namespace-blind walker, not verified — that's §2.5 territory); SEPA card schemes (`acmt.*`, `caaa.*`).

**Draft 19 polish:** schema-version detection landed — `sepaDetectDocType()` now reads the `Document`/wrapper `namespaceURI`, extracts the trailing `<msg>.<variant>.<version>` triple (e.g. `pain.001.001.03`), and surfaces it inline in the document-type row so users can distinguish pain.001.001.03 from .09 at a glance. The fallback when the namespace URI is absent or non-matching is the friendly mnemonic alone, so unknown / handwritten inputs degrade cleanly. Two new Playwright cases (`pain.001.001.03` banner; InstrId surfaced alongside EndToEndId). No new vendored deps, no CSP change, no tool-count change.

**Why:** Finance/accounting developers across the EU need to debug payment files. No good browser-based tool exists.

**Spec:**
- Accept SEPA ISO 20022 XML: `pain.001.001.{03,09}` (credit transfer initiation), `pain.008.001.{02,08}` (direct debit initiation), `camt.053.001.{02,08}` (bank-to-customer statement).

  - Header: message ID, creation datetime, initiating party, number of transactions.
  - Per-transaction table: end-to-end ID, amount + currency, debtor/creditor name + IBAN/BIC, remittance info, scheduled date.
  - Validation: schema-level sanity (required elements present), IBAN MOD-97 on each party (reuse §2.1), currency code is ISO 4217.
- Output: a pretty HTML table; one-click copy as CSV.

**Dependencies:** none (DOMParser is built in).

### 2.5 eIDAS digital signature inspector — PAdES / CAdES / XAdES

**Why:** EU has invested heavily in eIDAS qualified signatures. Free inspector tools are scarce, server-based, or paywalled.

**Spec:**
- **PAdES** (PDF signatures): parse the PDF, extract the `/Sig` dictionary, extract the embedded CMS `Contents` blob, hand off to the CAdES parser.
- **CAdES** (CMS / RFC 5652 + extensions): ASN.1 / DER parser (extend the existing X.509 parser — it already does ASN.1). Surface: signer info, signing certificate (chain if embedded), signing time, signature algorithm, content hash, attribute certificates, timestamp token (RFC 3161) if present, OCSP/CRL revocation info if embedded.
- **XAdES** (XML signatures): `DOMParser`-based. Surface the same fields. XAdES levels (B, T, LT, LTA) are detectable from the embedded properties.
- Output: a structured view of every property; raw ASN.1 / XML toggle for the curious.
- **No revocation checking against the network.** Tool reports what's in the signature; it does not contact OCSP responders or CRL endpoints.

**Dependencies:** none (extends the existing ASN.1 parser, reuses `DOMParser`).

**This is the largest tool in this spec. Plan ~1,500 lines and a multi-week effort.**

### 2.6 EU LOTL trust list viewer — **✅ shipped (draft 17)**

**Status notes (draft 17):** Landed as the `lotl` tool. The parser walks ETSI TS 119 612 XML by `localName` only, so the same code handles every minor revision (v2.1.1, v2.2.1, ...) without per-version branching.

- **LOTL mode** (`TSLType` ends in `EUlistofthelists`): renders the scheme operator + name + territory + issue/next-update dates, then one section per `<OtherTSLPointer>` with the country code (mined from `OtherInformation/SchemeTerritory`) and the `<TSLLocation>` URL.
- **TSL mode** (`TSLType` ends in `schemes/...`): renders the scheme metadata, then one section per `<TrustServiceProvider>` showing the TSP name, followed by each `<TSPService>` with type identifier (e.g. `Svctype/CA/QC`), status (e.g. `Svcstatus/granted`), and status starting time. - **Multi-language `<Name>` blocks**: ETSI lists carry `xml:lang`-tagged `<Name>` children inside `<SchemeName>`, `<SchemeOperatorName>`, `<TSPName>`, etc. The viewer prefers `xml:lang="en"` and falls back to the first child if no English variant is present.
- **No fetching**: the §0.2 / §2.6 "no network" rule is preserved — every parse run appends a footer note pointing the user to `ec.europa.eu` for the official LOTL file. No automatic resolution of `<TSLLocation>` URLs.

UI mirrors the SEPA tool layout (textarea + Parse button). ~190 lines of parser + render JS, ~25 new UI strings × 5 locales (en + fr + de reviewed against standard PKI/eIDAS terminology; zh-CN + hi machine-quality drafts pending native review per the project pattern). 5 SEO prose keys en-only via the existing Phase 7 carve-out.

### 2.8 EUDI Wallet credential decoder (SD-JWT and ISO mdoc) — **🟡 SD-JWT shipped (draft 20); ISO mdoc deferred**

**Status notes (draft 20):** SD-JWT support landed as an extension of the existing JWT inspector (no new top-level tool, no tool-count change — per the §2.8 spec's "already partly handled by the existing JWT inspector" framing). The JWT input field now detects the SD-JWT `~`-separator and:

- Splits the input into a leading JWT, zero or more disclosures, and an optional trailing key-binding JWT (KB-JWT detected by `dot.dot.dot` shape of the final segment).
- Decodes each disclosure as base64url → UTF-8 → JSON. Recognizes the two disclosure shapes from draft-ietf-oauth-selective-disclosure-jwt §5.2: `[salt, name, value]` for object claims and `[salt, value]` for array elements.
- Computes the SHA-256 digest over the wire-bytes of the disclosure (the literal base64url ASCII bytes, per §5.1.1) — not over the decoded JSON. The `_sd_alg` payload claim is honored (defaults to `sha-256` per §5.1).
- Walks the entire payload tree to collect every `_sd` digest array (top-level and nested under `vc`, `address`, etc.), then per-disclosure shows `✓ referenced in payload _sd` when the computed digest is present and `✗ unreferenced` when it is orphaned.
- Surfaces a present KB-JWT as a separate decoded JSON block (header + payload pretty-printed). Signature verification of the KB-JWT is out of scope for this slice — the existing JWT verify path covers the leading SD-JWT issuer signature, and the KB-JWT verification flow (audience, nonce, holder key resolution) is large enough to warrant its own slice if/when there's demand.

10 new UI strings (`jwt.sdjwt.{heading,colName,colValue,colSalt,colDigest,matched,orphan,arrayElem,kbJwt,parseErr}`) × 5 locales — en/fr/de reviewed against the SD-JWT draft's own vocabulary; zh-CN/hi machine-quality drafts pending native review per the project pattern. Three new Playwright cases (digest-matched disclosures, orphaned disclosure flagged, KB-JWT surfaced). Full suite: 235 → 238 passed. No new vendored deps, no CSP change.

**Deferred to a follow-up slice:**
- **ISO mdoc decoder.** Needs a small CBOR decoder (~300 lines, hand-rolled per ISO 18013-5's deterministic CBOR subset) plus COSE_Sign1 unwrapping for `MobileSecurityObject`. The CBOR decoder is also the natural prerequisite for any future COSE / WebAuthn attestation work, so it earns the vendor / hand-roll trade-off in its own slice.
- **KB-JWT signature verification.** Resolving the holder public key from the SD-JWT payload's `cnf` claim and verifying the KB-JWT signature with audience + nonce binding.
- **SD-JWT reconstructed payload view.** A toggleable "cleartext" rendering where each `_sd` digest is replaced with its disclosed claim, producing the post-disclosure JSON the verifier would actually consume.

**Why:** EU Digital Identity Wallet pilots are running now and the regulation forces member states to roll out wallets by 2026. The credential formats — SD-JWT (selective-disclosure JWT) and ISO 18013-5 mdoc (CBOR + COSE-signed) — are new and tooling is sparse.

**Spec:**
- **SD-JWT (`vc+sd-jwt`)**: parse the issuer-signed JWT (already partly handled by the existing JWT inspector), decode the disclosures (Base64URL-encoded JSON arrays), reconstruct the cleartext claim set, surface which claims are disclosed vs blinded.
- **ISO mdoc**: CBOR + COSE_Sign1. Needs a small CBOR decoder (~300 lines, hand-rolled; specifically the deterministic CBOR subset used by ISO 18013-5). Decode the `MobileSecurityObject`, surface namespaces, doctype, digests, validity, device key.
- **No verification against issuer trust anchors.** Tool decodes; does not verify the chain.

**Dependencies:** small hand-rolled CBOR decoder. Worth vendoring as `cbor.min.js` alongside the other deps.

**Risk:** the specs are still moving. Implement against the published ARF v1.x (Architecture and Reference Framework) and label the tool as "early — formats may change."

### 2.9 Argon2id KDF

**Why:** Modern PBKDF2 replacement. BSI, ANSSI, OWASP, and the Password Hashing Competition winners all recommend Argon2id.

**Spec:**
- Inputs: password (text), salt (text or hex), memory cost (KiB), time cost (iterations), parallelism (lanes), output length (bytes), variant (Argon2id default; offer Argon2i and Argon2d).
- Output: hex + PHC-formatted string `$argon2id$v=19$m=...,t=...,p=...$<b64-salt>$<b64-hash>`.
- Report wall-clock derivation time (same UX as the existing PBKDF2 tool).

**Dependencies:** This is the trade-off. Options:
1. **Vendored pure-JS Argon2** (e.g., `argon2-js`, ~30KB, ~10x slower than WASM). Acceptable for parameters typical of interactive logins (memory ~64MB, t=3). Painful for larger parameters.
2. **Vendored WASM Argon2** (`argon2-browser` core ~50KB Wasm). Fast. Requires the page to load WASM, which is a CSP change.

**Recommendation:** ship pure-JS first, label it "slower than native", and revisit WASM only if real users complain.

### 2.10 Ed25519 / X25519 standalone tools — **✅ shipped (draft 4)**

**Why:** Web Crypto now supports Ed25519 and X25519 natively (Safari 17, Chrome 113, Firefox 130). Useful for SSH, age, Signal, Noise, and many EU-origin protocols.

**Status notes (draft 4):** Shipped as two sister tools, `ed25519` and `x25519`. Both use native Web Crypto exclusively — no vendored JS, no WASM. Both detect lack of browser support and show an explicit banner with the minimum browser versions, rather than failing silently. Private keys are surfaced as the 32-byte RFC 8032 §5.1.5 seed (Ed25519) / RFC 7748 scalar (X25519); on import, the tool wraps the seed in the standard PKCS#8 / RFC 8410 envelope that Web Crypto requires. X25519 includes optional HKDF-SHA-256/SHA-512 post-processing with a user-supplied "info" context, matching Noise / X3DH conventions. Functional tests exercise RFC 8032 §7.1 vector 1 (empty message) and vector 2 (single byte `0x72`), a tampered-signature rejection, RFC 7748 §6.1 Alice/Bob shared secret derivation, and a round-trip generate→sign→verify; a11y verified in both themes.

**Spec:**
- **Ed25519:** generate keypair, sign (text or file), verify. Keys in raw 32-byte hex, OpenSSH format, and PEM (PKCS#8 / SPKI).
- **X25519:** generate keypair, compute shared secret given a peer public key. Keys in raw, PEM. Optionally pipe the shared secret through HKDF to produce a symmetric key (offer SHA-256 / SHA-512).

**Dependencies:** none — `window.crypto.subtle` handles both. Gracefully degrade on Safari < 17.

### 2.12 BLAKE2b / BLAKE3 hashes — **BLAKE2b ✅ shipped (draft 5); BLAKE3 deferred**

**Why:** Used by WireGuard, IPFS, Zcash, Filecoin, Borg backup, and other EU/global open-source projects. Modern, fast, and not in Web Crypto (which only does SHA-1/SHA-2).

**Status notes (draft 5):** BLAKE2b-512 shipped as an additional algorithm in the existing Hash & Checksum tool — no new tool view, no new top-level entry, just an extra row alongside SHA-1/SHA-256/SHA-384/SHA-512 in the output. ## 7. Tensions and non-goals

These are not deferred — they are **rejected** for this project.

1. **No PII validators.** Italian Codice Fiscale, Polish PESEL, Spanish DNI/NIE, German Steuer-ID, French INSEE/NIR, Dutch BSN, UK NINO, US SSN — all rejected. They are personally identifying numbers and a validator is borderline a data-handling tool. Commercial identifiers (IBAN, VAT, BIC, GS1, ISIN, CUSIP) are fine.
2. **No EU compliance theater.** Cookie banner generators, DPA templates, "GDPR audit checklists", "DPIA wizards", privacy-policy generators — all rejected. They are a different product and would dilute the focused, technical character of the site. Refer users to dedicated compliance products.
3. **No country auto-detection.** Locale comes from `navigator.language` and `localStorage`. The site does not infer country from IP, timezone, or any other signal. The same site is served to everyone.
4. **No "translation breadth over quality."** Five well-translated locales beat fifteen badly-translated ones. New locales ship only after Pass 3 (native review) of §1.3. The README's current note ("fr/de/zh/hi are machine-quality awaiting review") gets honored: those four go through native review *before* any new Tier 1 locale ships.
5. **No fetching trust lists or revocation data.** The eIDAS and LOTL tools (§2.5, §2.6) decode what you paste; they do not phone home. This is a feature, not a limitation.
6. **No WASM unless we have to.** Pure JS first. WASM only if a real user complains and there's no other way to deliver acceptable performance (the Argon2 trade-off in §2.9 is the canonical case).
7. **No build step beyond what already exists.** Vendored scripts only. No npm install, no bundler, no transpiler. If a new tool requires a real build system, it's not the right fit for this site.
8. **No telemetry of any kind.** Including "anonymous usage metrics" or "error reporting." If something breaks, users file an issue.
9. **No accounts, no sync, no cloud anything.** The single most-requested "feature" for tools like this. Permanent no.
10. **No mobile-app wrapper.** PWA install (§4.5) is enough. No Cordova, no Capacitor, no Tauri. The browser is the platform.

## 8. Acceptance criteria per workstream

A workstream is "done" when:

- **i18n infrastructure (Phase 1):** RTL renders correctly with `dir="rtl"` set on the existing site; plural strings use `Intl.PluralRules`; command palette accepts at least one French synonym and finds the right tool.
- **A new locale (Phases 2, 3, 8):** all 900 rows in `strings.csv` have `<locale>_status = reviewed`; all 7 passes (§1.3) completed and signed off; locale present in `hreflang`, language picker, `build-i18n-variants.js`; `/<locale>/index.html` exists and crawls; one external reviewer (native speaker, technically literate) has clicked through every tool in the locale and not flagged issues.
- **A new tool (Phases 4, 7):** runs offline (verified by disabling network in DevTools); CSP unchanged or extension justified; constant-time comparisons where applicable; output round-trips; existing test harness covers golden path; entry in `STRINGS` and in the command palette.
- **A regulator preset (Phase 6):** linked to the regulator's actual document (not a summary); dated in the help text; parameters in a JSON config (no hardcoded logic); audit-release script flags it for re-review one year out.
- **Distribution (Phase 5):** mirror pushes succeed automatically on tag; SHA-256s reproducible from a clean clone; onion address resolves; PWA install prompt fires on Chrome and Firefox.

## 9. Open questions

These need answers before the relevant phase starts:

- Who are the native reviewers? Building a small list of reviewers per Tier 1 locale (one per locale minimum) is a prerequisite to Phase 2. Reach out via privacy-tools mailing lists, Tor community, Codeberg communities.
- Is there appetite for a `MAINTAINERS.md` listing per-locale reviewers (with their consent) as a transparency measure?
- Should the single-file portable build (§4.6) be linked from the site itself or only from the repo? Linking from the site adds clarity but also adds a download that could lag the live site.
- For the EUDI Wallet decoder (§2.8): wait for the ARF to stabilize (likely mid-2026), or ship against the current spec and accept churn?
- For the Argon2 trade-off (§2.9): is the WASM CSP change worth the perf? Possibly skip Argon2 entirely until Web Crypto adds it natively (under discussion in W3C).

## 10. Maintenance

This spec is living. When a phase completes, update the rollout section to reflect what shipped. When a regulator preset's source document is superseded, update §3. When a translation glossary entry in §1.7 is corrected by a native reviewer, update the table and note the reviewer's pseudonym (with consent) and date.

The spec is the source of truth for *intent*; the code is the source of truth for *behavior*. Where they disagree, fix one or the other — never let the gap widen.
