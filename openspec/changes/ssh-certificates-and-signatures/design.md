# Design — SSH certificates, SSHSIG, private-key inspection, known_hosts / authorized_keys

## Context

All four formats are OpenSSH wire encodings (RFC 4251 §5: `string` = uint32 length + bytes, `uint32`, `uint64`, `mpint`) wrapped in Base64, and the parser already has `sshReadString()` and the public-key walker. The signature formats are the same ones SSH uses on the wire: an SSH signature blob is `string algorithm ‖ string signature`, where the inner signature is raw 64 bytes for `ssh-ed25519`, `mpint r ‖ mpint s` for `ecdsa-sha2-*`, and PKCS#1 v1.5 for `rsa-sha2-256` / `rsa-sha2-512` (and SHA-1 for legacy `ssh-rsa`). Web Crypto verifies all of these once the ECDSA mpints are left-padded to the curve width and the RSA key is imported as JWK from `e` and `n`.

Source documents: PROTOCOL.certkeys (certificate layout, option / extension names, the `0xFFFFFFFFFFFFFFFF` "forever" sentinel, the rule that the signature covers every preceding field), PROTOCOL.sshsig (magic `SSHSIG`, version 1, the signed-blob construction `SSHSIG ‖ string namespace ‖ string reserved ‖ string hash_alg ‖ string H(message)`, the requirement that RSA signatures use `rsa-sha2-256` / `-512`, and the explicit warning that the embedded key is informational), draft-josefsson-sshsig-format-04 (July 2026, the IETF write-up of the same format), PROTOCOL.key (`openssh-key-v1`: magic, ciphername, kdfname, kdfoptions = `string salt ‖ uint32 rounds`, nkeys, public keys, encrypted private block of checkint ×2, keys, comments, padding), `sshd(8)` (known_hosts hashed form `|1|base64(salt)|base64(HMAC-SHA1(salt, hostname))`, markers `@cert-authority` and `@revoked`, `[host]:port`; authorized_keys option grammar).

## Goals / Non-Goals

**Goals:**
- Every certificate field readable, every date human, every option and extension named, and the CA signature actually checked with the CA key fingerprint shown so the user can compare it to their `TrustedUserCAKeys`.
- SSHSIG verification that is honest about trust: the embedded key is displayed, the verification is run, and the "matches your allowed-signers key" row is what the summary turns on.
- Private-key files inspected without decryption, with the exact reason decryption is not offered.
- Hashed known_hosts lines answerable: "does this line belong to host X?"

**Non-Goals:**
- bcrypt_pbkdf / Blowfish: a hand-rolled Blowfish is ~120 lines plus the bcrypt hash and the OpenSSH pbkdf wrapper; deferred until asked. The Key Format Converter change handles unencrypted `openssh-key-v1` conversion.
- Git commit reconstruction: git signs the commit object with the `gpgsig` header removed; rebuilding it from `git cat-file -p` output is error-prone. The user pastes the exact bytes (`git cat-file commit <sha>` with the `gpgsig` lines stripped) and the info panel shows the one-liner to produce them. The tool does not guess.
- `sk-ssh-ed25519@openssh.com` / `sk-ecdsa-*` FIDO keys: parsed and displayed, signatures reported as "FIDO authenticator signature — not verified here".
- Certificate *issuance*, agent protocol, `ssh-keygen -L` parity for every OpenSSH version's text layout.

## Decisions

1. **One input, auto-detection by prefix.** `ssh-*` / `ecdsa-sha2-*` / `sk-*` → key or certificate (certificate when the type ends in `-cert-v01@openssh.com`); `-----BEGIN SSH SIGNATURE-----` → SSHSIG; `-----BEGIN OPENSSH PRIVATE KEY-----` → private-key inspection; a line starting with `|1|`, a hostname pattern, or `@cert-authority` / `@revoked` → known_hosts; a line whose first token contains `=` or is an option name → authorized_keys. Rejected: a mode selector (users do not know which of the five things they have).
2. **Certificate signature is verified over the exact bytes preceding the `signature` field**, sliced from the decoded blob — never re-encoded (the CSR decoder rule). The signature blob's inner algorithm name decides the hash: `rsa-sha2-512` → SHA-512, `rsa-sha2-256` → SHA-256, `ssh-rsa` → SHA-1 (verified via Web Crypto RSASSA-PKCS1-v1_5 with SHA-1 and labelled "legacy SHA-1 — refused by OpenSSH ≥ 8.8 by default"), ECDSA by curve, Ed25519 raw.
3. **Web Crypto for every signature and digest; pure JS for all framing.** RSA keys import as JWK `{kty: 'RSA', n, e}` with the SSH mpint stripped of its leading zero; ECDSA `r` / `s` mpints are left-padded or stripped to 32 / 48 / 66 bytes; Ed25519 uses the raw 32-byte key where the browser supports it (the Ed25519 tool's banner otherwise). HMAC-SHA-1 for known_hosts via `crypto.subtle.sign` with the 20-byte salt as key. Rejected: hand-rolled anything cryptographic.
4. **Validity window rows use `Intl` and a status word.** valid-after / valid-before as `Intl.DateTimeFormat` plus `Intl.RelativeTimeFormat`; `0xFFFFFFFFFFFFFFFF` renders as "forever"; the status row is "currently valid", "not yet valid", or "expired" against the browser clock, labelled as the browser clock.
5. **Critical options and extensions are decoded by the PROTOCOL.certkeys table; unknown names are shown raw.** `force-command` and `source-address` carry a `string` value, `verify-required` and all `permit-*` / `no-touch-required` extensions carry an empty string; an unknown *critical* option is flagged "unknown critical option — OpenSSH would refuse this certificate".
6. **SSHSIG: the signed blob is rebuilt, the message is hashed in-page.** `H(message)` with SHA-256 or SHA-512 per the `hash_algorithm` field over the pasted text (UTF-8, no newline normalisation — stated in the UI) or the loaded file; the blob `SSHSIG ‖ string ns ‖ string "" ‖ string hash_alg ‖ string H` is verified with the embedded key, then the embedded key is compared byte-for-byte with the user's allowed-signers key (the `principals [options] keytype base64` line format is parsed; `namespaces=`, `valid-before=` / `valid-after=` options are honoured in the rows). The RSA rule (`rsa-sha2-256` / `-512` only) is enforced as a ✗ row, not a silent accept.
7. **`openssh-key-v1`: parse the clear parts, stop at the ciphertext.** Header, kdfoptions (salt hex, rounds), nkeys, each public key with fingerprint; if cipher is `none`, the private block is parsed (checkint equality, key type, comment, padding check) and the comment shown — private scalars are never displayed; otherwise the row reads "encrypted with <cipher> / bcrypt (<rounds> rounds) — decryption needs bcrypt_pbkdf (Blowfish) and is deferred". The pasted file is treated as a secret field (masked, `clearSensitiveFields()`).
8. **known_hosts matching follows `sshd(8)` exactly.** Hashed entries: salt and hash Base64-decoded, HMAC-SHA-1(salt, hostname) compared in constant time; the user's hostname is tried as typed and as `[host]:port` when a port other than 22 is given. Plain entries: comma-separated patterns with `*` / `?` wildcards and `!` negation. Markers `@cert-authority` / `@revoked` are surfaced as rows. The tool can also *produce* the hashed form for a hostname with a fresh 20-byte salt so users can add entries by hand.
9. **authorized_keys lint as gate rows.** Option table from `sshd(8)` AUTHORIZED_KEYS FILE FORMAT; rows: unknown option, unbalanced quotes, `expiry-time=` parsed (`YYYYMMDD[HHMM[SS]]`, local time per sshd) and compared to now, `from=` pattern syntax, `command=` present without `restrict` (⚠ "consider `restrict`"), conflicting options (`restrict` with `no-*`), `cert-authority` on a non-key line, `permitopen=` / `permitlisten=` host:port syntax. Verdict language: "conforms to the sshd(8) option grammar", never "secure".

## Risks / Trade-offs

- **"Signature verifies" misread as "trusted".** The SSHSIG summary is driven by the allowed-signers comparison, and the certificate summary always shows the CA fingerprint with "compare to your TrustedUserCAKeys / @cert-authority entry". No green banner.
- **OpenSSH grammar drift.** New options (`verify-required`, `no-touch-required`) have appeared in recent releases; the tables are constants with the OpenSSH version they were checked against (9.9), and unknown names are displayed rather than rejected.
- **Browser Ed25519 support.** Same banner as the Ed25519 tool; most SSH keys today are Ed25519, so the banner is prominent when it applies.
- **Message newline handling in SSHSIG.** `ssh-keygen -Y sign` signs the file bytes exactly; a pasted text may gain or lose a trailing newline. The UI offers "append trailing newline" as a checkbox and says why.
- **Private-key file pasted into a browser.** Only the clear header is read, but the ciphertext is still in the field; the THREAT-MODEL.md endpoint caveat is repeated and the field is cleared on unload.
