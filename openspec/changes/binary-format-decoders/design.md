# Design — Binary Decoder

## Context

Four binary encodings, one input path. Input is hex, Base64 (standard or URL-safe), a `data:` / `otpauth-migration:` URI, or a dropped file; detection is by shape (hex alphabet, Base64 alphabet, URI scheme) with a manual override. The page's CBOR decoder (format tool) already owns a byte cursor with bounds checking, varint-like length reading and recursive rendering; the protobuf, MessagePack and bencode readers follow the same shape. SHA-1 / SHA-256 for info-hashes come from Web Crypto `digest`. The TOTP tool already parses `otpauth://` URIs and the Base64 / 32 / 58 encoder already has Base32 (RFC 4648 §6), which the migration decoder needs to turn raw secret bytes into the form `otpauth://` carries.

## Goals / Non-Goals

**Goals:**
- Any blob → something a human can read: hexdump always works; the structured decoders succeed or explain where they stopped (offset, expected / found).
- Schema-less protobuf that shows *every* plausible reading of a field rather than guessing one.
- Torrent info-hashes bit-exact with `transmission-show` / `aria2c -S` (hash over the original bytes).
- Authenticator export that gets the user from "QR on an old phone" to "`otpauth://` URIs loaded into the TOTP tool" without the secrets leaving the page.

**Non-Goals:**
- No `.proto` compiler, no descriptor-set loading, no `Any` type URL resolution.
- No MessagePack streaming (concatenated top-level values are decoded as a list and noted).
- No torrent creation, no piece verification against local files, no tracker / DHT / peer contact.
- No support for other authenticator apps' backup formats.
- No persistent storage of decoded secrets (no localStorage, no IndexedDB).

## Decisions

1. **Shared byte cursor.** The CBOR decoder's `{buf, pos, u8(), u16(), u32(), u64(), bytes(n)}` cursor is promoted to `ByteCursor` and reused by all three structured readers; each reader reports failure as `{offset, expected, found}` and the hexdump highlights that offset. Rejected: three independent readers — the CBOR one already handles the bounds and BigInt cases.
2. **Hexdump is canvas-free DOM text** in a monospace `<pre>`-like grid built with `createElement`, 16 bytes per row by default (8 selectable), offsets in 8 hex digits, non-printable bytes as `.` in the ASCII column (0x20–0x7E printable, matching `xxd`). Rows are virtualized above 64 KiB (render on scroll) to keep the 08-stress test green.
3. **Entropy per 256-byte window**, Shannon in bits/byte (0–8), rendered as a bar strip under the dump; a window ≥ 7.5 is labelled "high (compressed / encrypted / random)", ≤ 4 "low (text / structured)". The byte histogram is 256 bars. Rejected: chi-square or Monte-Carlo-π estimators — more numbers, no more insight for this audience.
4. **Strings extraction** scans ASCII runs (0x20–0x7E) and UTF-16LE runs (ASCII byte followed by 0x00) of ≥ 4 characters, as GNU `strings -a` / `strings -el` do; each hit links to its offset in the dump.
5. **Protobuf reader shows alternatives, not a guess.** Per the Protocol Buffers "Encoding" documentation (wire types 0 VARINT, 1 I64, 2 LEN, 5 I32, 3 SGROUP / 4 EGROUP deprecated): VARINT rows show unsigned, zigzag `sint`, and `bool` when 0 / 1; I64 rows show `fixed64`, `sfixed64`, `double`; I32 rows show `fixed32`, `sfixed32`, `float`; LEN rows try, in order, nested message (recursive parse that consumes every byte with valid tags and field numbers 1–536870911), UTF-8 string (valid UTF-8, no C0 controls except whitespace), packed repeated varints, and fall back to bytes (hex). Field numbers 19000–19999 are flagged reserved. Decoding uses BigInt for 64-bit; display uses `Intl.NumberFormat`. Rejected: committing to one reading — wrong half the time without a schema.
6. **MessagePack codec implemented from the spec's format table** (msgpack/spec.md): positive / negative fixint, fixmap, fixarray, fixstr, nil, false, true, bin 8/16/32, ext 8/16/32, float 32/64, uint 8–64, int 8–64, fixext 1–16, str 8/16/32, array 16/32, map 16/32. Timestamp extension type −1 (32-, 64-, 96-bit forms) is decoded to an ISO 8601 string. Binary (`bin`) becomes `{"$bin": "<hex>"}`, other `ext` becomes `{"$ext": type, "data": "<hex>"}`, 64-bit integers beyond 2^53 become strings with a note. Encoding JSON → MessagePack picks the smallest format per value and emits strings as `str`, never `bin`. Rejected: vendoring `msgpack-lite` (MIT, 25 KB) — the codec is ~150 lines.
7. **bencode reader tracks byte ranges** (`{start, end}` per value) so the info-hash is `SHA-1(buf.subarray(info.start, info.end))` over the *original* bytes, never over a re-encoding. BEP 3 grammar: `i…e` integers (leading zeros and `-0` flagged), `<len>:` byte strings (shown as UTF-8 when valid, else hex; `pieces` always hex-summarised), `l…e`, `d…e` with keys required sorted (⚠ when not). Torrent view: `info.name`, `piece length`, `pieces.length / 20`, `files[]` or single-file `length`, `announce` + `announce-list`, `creation date` via `Intl.DateTimeFormat`, `created by`, `comment`, `url-list` (BEP 19). v2 (BEP 52): `meta version 2` ⇒ info-hash = SHA-256(info), `file tree` rendered, `piece layers` counted; hybrid torrents show both hashes. Magnet (BEP 9): `magnet:?xt=urn:btih:<hex v1>` and `xt=urn:btmh:1220<hex v2>`, `dn`, `tr` parameters; rendered as text, never as a clickable link.
8. **Authenticator migration payload uses a reconstructed schema**, stated as such in the UI: `MigrationPayload { repeated OtpParameters otp_parameters = 1; int32 version = 2; int32 batch_size = 3; int32 batch_index = 4; int32 batch_id = 5; }` and `OtpParameters { bytes secret = 1; string name = 2; string issuer = 3; Algorithm algorithm = 4 (1 SHA1, 2 SHA256, 3 SHA512, 4 MD5); DigitCount digits = 5 (1 → 6, 2 → 8); OtpType type = 6 (1 HOTP, 2 TOTP); int64 counter = 7; }`. The `data=` parameter is URL-decoded then Base64-decoded (standard alphabet, as the app emits). The mapper is the schema-less protobuf reader plus this field map — no second parser. Each account becomes `otpauth://totp/<issuer>:<name>?secret=<Base32>&issuer=<issuer>&algorithm=SHA1&digits=6` (HOTP adds `&counter=`). Secrets render masked (`••••`) with a reveal toggle, the textarea and result nodes are cleared on view change, and nothing is written to storage.
9. **QR paths reuse the existing decoder and generator**: "scan export image" calls `qrDecodeImage(file)` (the draft-301 hand-rolled decoder) and feeds the resulting URI to the mapper; "render as QR" calls `qrcode.js` with the per-account `otpauth://` URI, error level M, as the QR Share tool does.
10. **Pure JS vs Web Crypto.** SHA-1 / SHA-256 for info-hashes: Web Crypto `digest`. Everything else (hexdump, entropy, protobuf, MessagePack, bencode, Base32, migration mapping): pure JS. No new primitive is hand-rolled.

## Risks / Trade-offs

- **Protobuf heuristics mis-type fields.** A `bytes` field that happens to parse as a nested message is shown as one; the UI labels the chosen reading "heuristic" and the alternatives remain one click away. The spec requires the hex reading to be always available.
- **Reconstructed migration schema.** Google has not published `MigrationPayload`; the field map is community-reconstructed and may change. Mitigation: unknown fields are shown raw rather than dropped, the UI says "reconstructed schema", and the test uses a synthetic payload built from the same map (self-consistency plus the publicly documented field numbers), not a real export.
- **Live secrets on screen.** A migration payload is the user's entire 2FA posture. Masking by default, clear-on-unload, no storage, and a red banner reading "this payload contains live 2FA secrets — close other tabs, do not screenshot" are mandatory; the threat model (compromised endpoint) still applies and is linked.
- **Large files.** A 50 MB `.torrent` (`pieces` is 20 bytes per piece) or a multi-megabyte protobuf would freeze the main thread if fully rendered. Decoding is streamed with `requestAnimationFrame` yields above 1 MiB and the hexdump is virtualized; the strings scanner caps at the first 10,000 hits.
- **False confidence.** Decoding a torrent or a protobuf proves structure, not provenance. The torrent view reads "info-hash computed from the file as given — this does not establish what content the swarm serves or whether it is lawful to download."
