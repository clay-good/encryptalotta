# Design — Supply-Chain Artifact Inspector

## Context

Five artifact families, one view, one rule: the user supplies every trust anchor. The formats are all JSON (or XML for CycloneDX / SPDX tag-value excluded) wrapping Base64 blobs the page already knows how to read — DER certificates (the `tls-cert` ASN.1 reader), raw Ed25519 / ECDSA / RSA signatures (Web Crypto `verify`), SHA-256 digests (`digest`), BLAKE2b-512 (inline), RFC 3161 `TimeStampToken` (decoder from `eidas-signature-cryptographic-verification`). Governing documents: CycloneDX 1.6 specification (ECMA-424), SPDX 2.3 and 3.0 specifications (ISO/IEC 5962:2021 for 2.2.1), in-toto Attestation Framework (Statement v1) and DSSE v1.0 (secure-systems-lab/dsse), SLSA Provenance v1, Sigstore protobuf-specs (`Bundle` v0.3), Rekor OpenAPI (`hashedrekord` v0.0.1, `intoto` v0.0.2, `dsse` v0.0.1), RFC 6962 §2.1 Merkle hashing, the C2SP `tlog-checkpoint` and `signed-note` formats, Fulcio certificate-specification OIDs, minisign and signify file formats, cosign `sign-blob` key mode.

## Goals / Non-Goals

**Goals:**
- Read any of the five families and say exactly what is inside, with Base64 decoded and times localized.
- Every cryptographic check runs offline against a key or root the user pastes; each is one ✓ / ✗ row that names the clause.
- The site's own artifacts (`sbom.json` + vendored libs; `RELEASES.md` + `.minisig` + pinned key) are the worked examples and must verify in the page.

**Non-Goals:**
- No network: no Rekor lookup by log index, no Fulcio / TUF root download, no OSV queries.
- No SBOM diffing, merging or generation; no license-compatibility analysis (license ids are shown, not judged).
- No SPDX tag-value or RDF/XML; no CycloneDX protobuf.
- No keyless *signing*, no cosign bundle *creation*, no Rekor upload.
- No chain building beyond leaf → (intermediates in the bundle) → pasted root; no CRL / OCSP (§7.5).

## Decisions

1. **One tool, family auto-detected from the first bytes / keys**: `bomFormat: "CycloneDX"` or `<bom xmlns="http://cyclonedx.org/schema/bom/…">`; `spdxVersion` / `@context` with `spdx.org/rdf/3.0`; `payloadType` + `signatures[]` = DSSE; `mediaType: application/vnd.dev.sigstore.bundle.v0.3+json` (and `.v0.1` / `.v0.2`, reported as older); `untrusted comment:` first line = minisign / signify; otherwise a bare Base64 blob with a `.sig` name = cosign. A manual override exists. Rejected: five tools — they share the digest-of-dropped-file and pasted-key panels.
2. **SBOM mapping to one internal component model** `{name, version, purl, licenses[], hashes{alg: hex}, type, supplier}` from CycloneDX `components[]` (+ `metadata.component`) and SPDX `packages[]` (`externalRefs` with `referenceType purl`, `checksums[]`, `licenseConcluded` / `licenseDeclared`); dependency counts from CycloneDX `dependencies[]` and SPDX `relationships[]` (`DEPENDS_ON`). SPDX 3.0 JSON-LD is walked structurally (`@graph` elements of type `software_Package`) without a JSON-LD processor; the gate says "structural read, not JSON-LD expanded". CycloneDX XML goes through the UBL inspector's `DOMParser` path. Format-version gate: CycloneDX 1.4–1.6 ✓, 1.3 and below ⚠ "superseded", unknown ✗; SPDX 2.3 ✓, 2.2 ⚠, 3.0 ⚠ "structural". Rejected: vendoring the CycloneDX JS library (Apache-2, 180 KB, needs a bundler — §7.7).
3. **Hash cross-check matches dropped files to components by file name**, then by any declared hash (so a renamed file still matches), computing SHA-256 / 384 / 512 with `crypto.subtle.digest` and comparing constant-time. CycloneDX `hashes[].alg` names `SHA-256` / `SHA-384` / `SHA-512` / `BLAKE2b-512` / `SHA3-256` map to the engines already on the page; MD5 and SHA-1 declared hashes are reported "declared but not computed on this site" (⚠, weak algorithm). "SBOM has no hashes" is a ⚠ for the whole document.
4. **DSSE PAE is built byte-exact**: `"DSSEv1" SP len(type) SP type SP len(payload) SP payload` with decimal ASCII lengths over UTF-8 / raw bytes (DSSE §Protocol). Signature algorithm is inferred from the pasted key: PEM SPKI → `crypto.subtle.importKey('spki')`; raw 32-byte Ed25519 → the JWK tool's 12-byte prefix; `ssh-ed25519` / `ecdsa-sha2-nistp256` lines → the SSH Key Parser's wire reader. ECDSA signatures arrive DER-encoded (cosign / Sigstore) and are converted to the raw `r ‖ s` form Web Crypto expects via the ASN.1 reader; RSA uses RSASSA-PKCS1-v1_5 or PSS by user toggle (cosign defaults to PKCS1-v1_5 with SHA-256). `keyid` is displayed and, when the key is pasted, compared with SHA-256 of the key's SPKI DER (the convention Sigstore uses).
5. **in-toto / SLSA rendered from the Statement, not validated against JSON Schema**: `_type == https://in-toto.io/Statement/v1`, `subject[]` (name, `digest.sha256` / `sha512` / `gitCommit`), `predicateType`; for `https://slsa.dev/provenance/v1` the fields `buildDefinition.buildType`, `externalParameters`, `internalParameters`, `resolvedDependencies[]` (uri, digest), `runDetails.builder.id`, `runDetails.metadata.invocationId / startedOn / finishedOn`; other predicate types are pretty-printed. Rejected: a JSON Schema validator (would be a new engine for little gain; the fields that matter are rendered and gated).
6. **Sigstore bundle verification is five independent rows**, each computable offline from the bundle plus pasted material: (a) `messageSignature.messageDigest` (or the DSSE subject digest) equals SHA-256 of the dropped artifact; (b) the signature verifies with the leaf certificate's SPKI (or the `publicKey` hint's pasted key); (c) RFC 6962 §2.1 inclusion: `leafHash = SHA-256(0x00 ‖ canonicalizedBody)`, fold `hashes[]` by `logIndex` / `treeSize` bit path with `SHA-256(0x01 ‖ left ‖ right)`, compare with `rootHash` and with the root in the checkpoint's note body; (d) the checkpoint `signed-note` signature (Ed25519 or ECDSA P-256 per the note's key-hint byte layout: 4-byte key hash ‖ signature) verifies with the pasted Rekor public key, whose first 4 SHA-256 bytes must match the hint; (e) leaf → bundle intermediates → pasted Fulcio root chain verifies (signature over `tbsCertificate` with the issuer key, basicConstraints / keyUsage checks from the `x509-chain-and-lint` change where available, else a local minimal path check), and `integratedTime` or the RFC 3161 `genTime` lies within the leaf's `notBefore` / `notAfter` (Fulcio leaves live ~10 minutes, so this check is what binds the signature to the OIDC identity). Fulcio OIDs decoded: `1.3.6.1.4.1.57264.1.1` issuer (deprecated, raw), `.8` issuer (DER UTF8String), `.9` build signer URI, `.10` build signer digest, `.11` runner environment, `.12` source repository URI, `.13` source repository digest, `.14` source repository ref, `.15` source repository identifier, `.16` source repository owner URI, `.17` owner identifier, `.18` build config URI, `.19` build config digest, `.20` build trigger, `.21` run invocation URI, `.22` source repository visibility; SAN `rfc822Name` / `uniformResourceIdentifier` shown as the signing identity. Rekor body kinds: `hashedrekord` (data.hash, signature.content, publicKey.content), `intoto` v0.0.2 (envelope hash, payload hash), `dsse` v0.0.1 (envelope hash, payload hash, signatures). Rejected: implementing the Sigstore "verification policy" language (identity + issuer matching) — the identity is *displayed*; the user judges it.
7. **minisign / signify parser mirrors `scripts/verify-release-signature.js` line for line** (same byte layout, same key-id little-endian display) so the in-page result and the CI result cannot disagree. `ED` prehashed: `Ed25519(BLAKE2b-512(file))` with the inline BLAKE2b; `Ed` legacy: `Ed25519(file)`; global signature `Ed25519(sig ‖ trusted_comment)`. signify differs only in having no trusted-comment line and no `ED` mode; the parser detects the two-line form. Public key `RWS…` = Base64(`Ed` ‖ keyId ‖ pk); the SECURITY.md key `RWSF2o7wI6QqGgABIako11R3e1+V9trHpv6k0b4vNPw/Q/qXnRXTtVX0` (key id `1A2AA423F08EDA85`) is offered as a one-click preset labelled "encryptalotta release key as pinned in SECURITY.md — still a key you choose to trust". Ed25519 verify: Web Crypto (`Ed25519` algorithm, shipped in all evergreen browsers; the Ed25519 tool already relies on it).
8. **cosign key mode**: `.sig` is Base64 of a DER ECDSA signature over SHA-256 of the blob; `cosign.pub` is PEM SPKI P-256. Verify with `crypto.subtle.verify({name: 'ECDSA', hash: 'SHA-256'})` after DER → raw conversion. RSA and Ed25519 cosign keys are accepted too (cosign supports them) with the same key-import path as decision 4.
9. **Pure JS vs Web Crypto, per primitive**: SHA-256 / 384 / 512 → Web Crypto `digest`; Ed25519, ECDSA P-256 / P-384, RSA PKCS1-v1_5 / PSS → Web Crypto `verify`; BLAKE2b-512, SHA3-256 → existing inline engines; X.509 / DER / TimeStampToken parsing → inline ASN.1 reader; RFC 6962 Merkle fold, PAE, DER ↔ raw ECDSA conversion, Base64 / PEM handling → pure JS. No new hand-rolled primitive.

## Risks / Trade-offs

- **Trust-anchor confusion.** A ✓ in every row means "verifies against the key / root *you* pasted". The summary line says so verbatim and the release-key preset is explicitly a convenience, not an endorsement. The LOTL viewer sets the precedent.
- **Sigstore format churn.** Bundle v0.1 / v0.2 (`tlogEntries[].inclusionPromise` only, no checkpoint) are decoded with row (c) and (d) reading "not available in this bundle version" rather than ✗. The protobuf-specs media type is version-checked and the version printed.
- **Checkpoint signature key types.** Rekor public instances sign checkpoints with ECDSA P-256; private instances may use Ed25519. The signed-note parser reads the 4-byte key hint and tries the pasted key's type; mismatch is a ✗ naming the hint.
- **X.509 path checks.** Full RFC 5280 path validation belongs to `x509-chain-and-lint`; until it lands, row (e) performs signature chaining plus validity-window and basicConstraints only and labels itself "minimal path check".
- **Large SBOMs.** A 40,000-component SBOM renders slowly in a single table; rows virtualize above 2,000 components and the hash cross-check only touches components with a dropped file.
- **False confidence on SBOM content.** An SBOM with matching hashes proves the listed files are the listed files, not that the list is complete or the versions free of CVEs. The summary says "hashes match the SBOM you supplied — this does not establish completeness or absence of vulnerabilities."
