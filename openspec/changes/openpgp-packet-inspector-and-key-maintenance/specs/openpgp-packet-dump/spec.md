# Spec Delta — openpgp-packet-dump

## Purpose

Show any OpenPGP key, message, or signature as the RFC 9580 packet sequence it is — tags, versions, header and length encodings, byte offsets, and every per-packet field with its RFC name — using OpenPGP.js's packet list for bodies and a header-only walker for offsets, entirely in the browser.

## ADDED Requirements

### Requirement: Input and object detection
The tool SHALL accept ASCII-armored text (any `-----BEGIN PGP …-----` block), a binary file, or hex / Base64 bytes; SHALL select `readKey`, `readPrivateKey`, `readMessage`, or `readSignature` from the armor header or the first packet tag; and SHALL still list tags, lengths, and offsets from the header walker when OpenPGP.js rejects the object, naming the rejection.

#### Scenario: Armored public key
- **WHEN** a `-----BEGIN PGP PUBLIC KEY BLOCK-----` is pasted
- **THEN** the dump lists packets in order with tag numbers and names (6 Public-Key, 13 User ID, 2 Signature, 14 Public-Subkey, 2 Signature) and the armor CRC-24 result

#### Scenario: Unknown algorithm fallback
- **WHEN** a key packet carries a public-key algorithm ID that OpenPGP.js 6.3.2 rejects
- **THEN** the walker rows still show tag, length, offset, version, and the algorithm ID byte with "unknown to OpenPGP.js 6.3.2 — IDs in this range are assigned by RFC 9980 (PQC)"

### Requirement: Header, length, and offset rendering
The tool SHALL show for each packet its header format (OpenPGP or legacy, RFC 9580 §4.2), the length encoding (one-octet, two-octet, five-octet, partial-body §4.2.1), header and body byte counts, and the zero-based byte offset of the header in the binary stream; offsets SHALL be contiguous and SHALL sum to the stream length.

#### Scenario: Contiguous offsets
- **WHEN** a key generated by the page is dumped
- **THEN** each packet's offset equals the previous packet's offset plus its header and body lengths, and the final sum equals the dearmored byte length

#### Scenario: Legacy-format header
- **WHEN** a key written with legacy-format headers is dumped
- **THEN** the header column reads "legacy format, length type n" for those packets and the body fields still render from OpenPGP.js

### Requirement: Key packet fields
The tool SHALL render for Public-Key, Public-Subkey, Secret-Key, and Secret-Subkey packets (RFC 9580 §5.5): version (4 or 6), creation time with `Intl.DateTimeFormat`, public-key algorithm by §9.1 name, key size or curve, fingerprint and key ID; and for secret packets the S2K usage octet, S2K specifier by §3.7.1 name (simple, salted, iterated-salted with the decoded count, Argon2 with t / p / m), the symmetric or AEAD algorithm, and whether the key material is encrypted.

#### Scenario: Argon2 S2K
- **WHEN** a v6 secret key protected with Argon2 is dumped
- **THEN** the secret-key row reads "S2K: Argon2 (type 4), t=…, p=…, m=2^…", AEAD OCB, and "key material encrypted"

### Requirement: Signature packet fields
The tool SHALL render for Signature packets (RFC 9580 §5.2): version (4 or 6), signature type by §5.2.1 name and hex code, public-key and hash algorithms by §9 name, the left 16 bits of the signed hash, the salt length for v6, and the counts of hashed and unhashed subpackets.

#### Scenario: Subkey binding signature
- **WHEN** the signature after a Public-Subkey packet is expanded
- **THEN** it reads type 0x18 Subkey Binding, names the public-key and hash algorithms, and shows the two subpacket counts

### Requirement: Signature subpacket rendering
The tool SHALL list hashed and unhashed subpackets separately, naming each per RFC 9580 §5.2.3.7 — creation time, signature and key expiration (with the resulting date), key flags with every bit named, preferred symmetric / hash / compression / AEAD algorithms, features, issuer key ID, issuer fingerprint, notation name and value, intended recipient, embedded signature rendered recursively — and SHALL mark the critical bit.

#### Scenario: Key flags named
- **WHEN** a binding signature carries key flags `0x0C`
- **THEN** the subpacket row reads "key flags: encrypt communications, encrypt storage"

#### Scenario: Unhashed versus hashed
- **WHEN** a signature carries the issuer key ID in the unhashed area
- **THEN** it appears under "unhashed subpackets" with the note that unhashed subpackets are not covered by the signature

### Requirement: Message packet fields
The tool SHALL render PKESK (version, recipient key ID or fingerprint, algorithm), SKESK (version, S2K, cipher / AEAD), SEIPD (version; v1 "with MDC"; v2 cipher, AEAD mode by §9.6 name, chunk size), Compressed Data (algorithm by §9.4 name), Literal Data (format letter, filename, date), One-Pass Signature, Marker, and Padding (tag 20) packets, and SHALL show encrypted bodies as opaque byte counts without attempting decryption.

#### Scenario: SEIPD v2 message
- **WHEN** a message encrypted by the page's Encrypt tool with AEAD is dumped
- **THEN** the SEIPD row reads "version 2, AES-256, OCB, chunk size 2^…" and the body is shown as "n bytes ciphertext — decrypt with the Decrypt tool"

### Requirement: Offline operation and verdict language
The tool SHALL dump without any network request, SHALL not decrypt or verify anything in this tab, and SHALL describe the output only as "structure per RFC 9580", never as the key or message being valid or trusted.

#### Scenario: Input never leaves the page
- **WHEN** a private key is dumped while the browser's network log is observed
- **THEN** no request of any kind is issued (the document CSP is `connect-src 'none'`)

#### Scenario: Result wording
- **WHEN** a dump completes without parser errors
- **THEN** the status line reads "n packets, m bytes — structure per RFC 9580; signatures are not verified in this view" and contains neither "valid" nor "trusted"
