# Design — Checksums, non-cryptographic hashes, and hash identification

## Context

The Hash & Checksum view (`#hash-view`) has a text / file input, a results list, a constant-time comparison pair (`#hash-a` / `#hash-b`), and an "advanced" `<details>` with BLAKE2b keyed / BLAKE3 modes / SHAKE. Every primitive here is small integer arithmetic — the natural fit for hand-rolled pure JS, which is the house norm (BLAKE3, Keccak, Reed-Solomon all live inline). Web Crypto contributes only `digest()` for the SHA family in the manifest check. The CRC RevEng catalogue (Greg Cook) defines each CRC by seven parameters and a `check` value — the CRC of the ASCII string `123456789` — which makes every preset self-verifying.

## Goals / Non-Goals

**Goals:**
- One CRC engine, any parameters; ten presets each proven by its RevEng `check` value at load time in the test suite.
- Eight non-cryptographic hashes with their authors' published vectors, visibly labelled as integrity-only.
- An identifier that says "candidates", never "this is", and decodes parameters where the format carries them.
- `sha256sum -c` in the browser, with the same three outcomes (OK / FAILED / missing).

**Non-Goals:**
- No MD5 / MD4 / NTLM / SHA-0 computation. The identifier names them as candidates only.
- No hash cracking, dictionary or rainbow lookup, no "is this password hash weak" beyond the parameter comparison.
- No CRC parameter recovery from samples.
- No streaming of multi-gigabyte files in slice 1: files are read whole via `arrayBuffer()`; a ⚠ appears above 512 MiB.

## Decisions

1. **Generic CRC engine, two code paths.** For `refin = true` with width ≥ 8 the engine builds a 256-entry table (reflected polynomial, `Uint32Array` for width ≤ 32, `BigUint64Array` for 64) — the zlib / Castagnoli / XZ case. For `refin = false` or width < 8 it runs the bitwise MSB-first loop. Both are parametrised by `{width, poly, init, refin, refout, xorout}` exactly as RevEng prints them; `check` is stored with each preset and asserted in the tests. Rejected: a per-preset hand-written function each — ten near-copies, no custom mode.
2. **Presets are the RevEng catalogue rows, cited by name:** CRC-8 (`poly 07 init 00 check F4`), CRC-16/CCITT-FALSE (`1021 FFFF → 29B1`), CRC-16/MODBUS (`8005 FFFF refin refout → 4B37`), CRC-16/XMODEM (`1021 0000 → 31C3`), CRC-16/ARC (`8005 0000 refin refout → BB3D`), CRC-32 (`04C11DB7 FFFFFFFF refin refout xorout FFFFFFFF → CBF43926`), CRC-32C (`1EDC6F41 … → E3069283`), CRC-32/BZIP2 (`04C11DB7 FFFFFFFF no reflect xorout FFFFFFFF → FC891918`), CRC-64/ECMA-182 (`42F0E1EBA9EA3693 init 0 → 6C40DF5F0B497347`), CRC-64/XZ (`42F0E1EBA9EA3693 init all-ones refin refout xorout all-ones → 995DC9BBDF1939FA`). The reflected-form polynomials the brief lists (`EDB88320`, `82F63B78`) are shown as "reflected form" beside the normal form.
3. **64-bit arithmetic with BigInt** for CRC-64, FNV-64, xxHash64 and SipHash; 32-bit functions use `Math.imul` and `>>> 0`. Rejected: 64-bit emulation with two 32-bit halves — faster, but the brief's budget is correctness and readability.
4. **Non-cryptographic hash vectors, each named in the spec**: Adler-32 of `Wikipedia` = `11E60398` and the RevEng-style check over `123456789` = `091E01DE` (RFC 1950 §8.2); Fletcher-16 of `abcde` = `C8F0`, Fletcher-32 of `abcde` = `F04FC729` (Wikipedia / Fletcher 1982 reference values); FNV-1a 32 of `a` = `E40C292C`, FNV-1a 64 of `a` = `AF63DC4C8601EC8C`, FNV-1 32 of empty = `811C9DC5` (Noll's reference list); xxHash32 of empty seed 0 = `02CC5D05`, xxHash64 of empty seed 0 = `EF46DB3751D8E999` (xxHash repository `xxhsum` vectors); MurmurHash3 x86_32 of empty seed 0 = `00000000`, of `hello` seed 0 = `248BFA47` (Appleby's `SMHasher` reference); SipHash-2-4 of the 15-byte message `00 01 … 0E` with key `00 01 … 0F` = `A129CA6149BE45E5` (the vector in the SipHash paper, Aumasson & Bernstein 2012, Appendix A). Each result row cites its source.
5. **SipHash is labelled a keyed PRF.** The panel shows the 128-bit key field as required, explains that SipHash-2-4 is a MAC-like function designed against hash-flooding (and that the site's HMAC tool is the right choice for message authentication), and does *not* appear under the "checksum" heading. Rejected: omitting SipHash — it is the one function here people actually need to reproduce from a Python / Rust runtime.
6. **Identifier is a rule table, not a classifier.** ~60 ordered rules of `{test: RegExp | fn, candidates: [...], decode?: fn}`; the first matching structured rule (prefix formats) wins outright, otherwise all length / alphabet rules that match are listed as candidates in catalogue order. Structured formats: PHC (`$<id>$[v=…$]<params>$<salt>$<hash>`, with `argon2id` / `argon2i` / `argon2d` / `scrypt` / `pbkdf2-sha256` / `pbkdf2-sha512` ids), bcrypt `$2a$ $2b$ $2y$<cost>$<22 salt><31 hash>`, Unix crypt `$1$` MD5 / `$5$` SHA-256 / `$6$` SHA-512 (with `rounds=`) / `$7$` scrypt / `$y$` yescrypt, LDAP `{SSHA} {SHA} {CRYPT} {MD5} {SMD5}`, Django `<algorithm>$<iterations>$<salt>$<hash>`, Rails / Devise (bcrypt), Drupal 7 `$S$`, OpenSSH `SHA256:<43 base64>`, SRI `sha256-` / `sha384-` / `sha512-`, Git 40-hex / 64-hex object ids (candidate, not winner), Base58Check (decode via the encoder; version byte named), hex and Base64 digests by length (16 / 20 / 28 / 32 / 48 / 64 bytes). PHC parameters are decoded (`m`, `t`, `p`; `ln`, `r`, `p`; iterations) and compared with the Argon2 tool's OWASP preset (m = 19 MiB, t = 2, p = 1) or the PBKDF2 tool's NIST / OWASP preset; the verdict is "at or above / below the OWASP minimum", nothing stronger. Rejected: a probabilistic "hashid"-style scorer — opaque, and still wrong for bare hex.
7. **Manifest parser accepts the four common shapes**: GNU `<hex>  <name>` (two spaces; `*` marks binary mode), BSD `SHA256 (<name>) = <hex>` and `BLAKE2b (<name>) = …`, bare `<hex>` single-line `.sha256` / `.md5` sidecar files (name taken from the manifest file name minus extension), and `<hex> <name>` single-space. Algorithm is inferred from the digest length and the BSD tag, with a selector override: 32 hex → MD5 (reported as "cannot verify: MD5 not computed on this site"), 40 → SHA-1, 64 → SHA-256 or BLAKE2s / SHA3-256 (selector), 96 → SHA-384, 128 → SHA-512 or BLAKE2b-512 (selector; `b2sum` output has the BSD tag). Files are matched by base name; comparison is the existing constant-time function; outcomes are OK / FAILED / missing exactly as `sha256sum -c` prints, plus "extra file not in manifest".
8. **Pure JS vs Web Crypto.** CRC family, Adler, Fletcher, FNV, xxHash, Murmur, SipHash: pure JS (hand-rolled, no vendored library). Manifest digests: Web Crypto `digest` for SHA-1 / 256 / 384 / 512; the existing hand-rolled BLAKE2b and Keccak for `b2sum` / `sha3sum` lines. Base58Check: the encoder's existing SHA-256d path.

## Risks / Trade-offs

- **Misuse of non-cryptographic hashes.** A CRC-32 "match" means the file is intact, not authentic. The banner on every result row in these two panels reads "integrity only — detects corruption, not tampering"; the manifest panel adds "a manifest that travelled with the file proves nothing about the file — verify the manifest's signature (PGP Verify)".
- **Identifier false certainty.** A 64-hex string is SHA-256 *or* SHA3-256 *or* BLAKE2s *or* a Git SHA-256 object id *or* random hex; the output always says "candidates" and lists them all. The spec forbids a single-answer phrasing for bare digests.
- **BigInt performance.** CRC-64 and xxHash64 over a 500 MB file in BigInt are slow (tens of seconds). Mitigation: the 64-bit table path processes 8 bytes per lookup where the algorithm allows; a progress bar and the 512 MiB ⚠. WASM stays off the table (§7.6) until a user complains.
- **Manifest encodings.** GNU coreutils escapes newlines and backslashes in file names (`\` prefix line); the parser handles the `\` prefix and `\n` / `\\` escapes and otherwise reports "name could not be parsed" rather than guessing.
- **Scope creep toward cracking.** Decoding bcrypt cost or Argon2 memory is one step from "estimate crack time". The spec limits the verdict to the OWASP comparison and links to the Passphrase Strength Estimator for anything about the password itself.
