# Design — Email authentication verification

## Context

`mailhdr` already unfolds and parses RFC 5322 headers, keeps them in received order, reads `Authentication-Results`, and computes an organizational-domain approximation (exact or subdomain match, no Public Suffix List). Verification needs three more things it does not have: the message *body* (for `bh=`), the signer's *public key* (from DNS), and canonicalization. The first two come from the user — the body is already in the pasted raw message, the key is one `dig` away — and canonicalization is string processing defined precisely in RFC 6376 §3.4. Signature verification itself is Web Crypto: `RSASSA-PKCS1-v1_5` with SHA-256 for `a=rsa-sha256`, `Ed25519` for `a=ed25519-sha256`.

SPF, DMARC, and the DNS record linters are parsers over short text records with published grammars. SPF evaluation (RFC 7208 §4) is normally recursive over DNS; here recursion is bounded by what the user pastes, and the tool says which `include:` targets it could not expand.

## Goals / Non-Goals

**Goals:**
- A failed DKIM signature is explained at the level where it failed: key unparseable → body hash mismatch → signature mismatch, each with what to check.
- The RFC 6376 and RFC 8463 appendix examples verify in the page, pinning the canonicalizers.
- SPF and DMARC lints say what a receiver would do with the record, in RFC terms, and point at the RFC 9989 changes.
- Every panel works with nothing but pasted text; nothing is fetched.

**Non-Goals:**
- No DNS, no DNSSEC chain to the root, no CT / certificate lookups.
- No `a=rsa-sha1` acceptance beyond "historic, treated as fail" (RFC 8301 §3.1).
- No DMARC aggregate / failure report parsing (RFC 9990 / 9991).
- No MIME decoding of the body for display; the body is bytes for hashing only.
- No BIMI SVG rendering; the `l=` URL and `a=` VMC URL are displayed as text.

## Decisions

1. **Input model: one raw message, plus a "DNS records" textarea.** The records textarea accepts any mix of pasted `dig` output lines or bare records; a classifier recognises `v=DKIM1`, `v=spf1`, `v=DMARC1`, `v=STSv1`, `v=TLSRPTv1`, `v=BIMI1`, TLSA (`usage selector matching hex`), CAA (`flags tag "value"`), DNSKEY / DS (RFC 4034 presentation format), and MTA-STS policy files (`version: STSv1`). The user never has to pick a type. Rejected alternative: one textarea per record type — eight boxes for a flow that usually needs two.
2. **DKIM key association by `d=` + `s=`.** A `v=DKIM1` record is matched to a signature when the pasted line carries the owner name `<s>._domainkey.<d>` (from `dig` output) or, failing that, when only one key and one signature exist; otherwise the user is asked to prefix the record with its selector. `k=rsa` (default) and `k=ed25519` keys are supported; `h=` (acceptable hash algorithms), `t=y` (testing), `t=s` (strict subdomain), `s=email` service type are honoured per RFC 6376 §3.6.1.
3. **Canonicalization is implemented literally from RFC 6376 §3.4** on the raw bytes (CRLF normalised from bare LF since pasted text loses CR): *simple* body removes trailing empty lines and ensures one CRLF; *relaxed* body collapses WSP runs, strips trailing WSP, removes trailing empty lines; *simple* header is byte-identical; *relaxed* header lowercases the field name, unfolds, collapses WSP, strips WSP around the colon. `l=` truncates the canonical body before hashing and is flagged ⚠ (RFC 6376 §8.2 body-length attack note). Rejected alternative: regex-only relaxed header — breaks on folded headers with tabs.
4. **Header selection follows RFC 6376 §5.4.2 exactly**: for each name in `h=`, take the *last* unused instance from the bottom of the header block; non-existent names contribute nothing but are shown ("signed as absent — oversigning"); then the DKIM-Signature header itself with `b=` emptied, canonicalized, without trailing CRLF. The data hashed is the concatenation of the selected canonical headers and this final header.
5. **Signature verification via Web Crypto only.** RSA: `p=` base64 → SPKI DER → `crypto.subtle.importKey('spki', …, {name:'RSASSA-PKCS1-v1_5', hash:'SHA-256'})` → `verify`. The modulus length is read with the hand-rolled ASN.1 reader for the key-length gate (< 1024 ✗ per RFC 8301 §3.2; 1024 ⚠; ≥ 2048 ✓). Ed25519: 32-byte raw key → SPKI wrapper (the fixed 12-byte prefix the JWK tool already uses) → `importKey('spki', …, 'Ed25519')`; browsers without Ed25519 in Web Crypto report "verification unavailable in this browser" rather than failing the signature. Rejected alternative: a pure-JS RSA — pointless when Web Crypto has it; the site's pure-JS Ed25519 is for key generation, not needed here.
6. **Body hash first, then signature.** `bh=` is compared before any signature math so a mismatch is reported as such ("body changed in transit or `c=` mismatch"), the most common failure. `t=` / `x=` are shown as dates with relative time; an expired `x=` is ✗ (RFC 6376 §6.1.1), a future `t=` ⚠.
7. **SPF evaluation is RFC 7208 §4.6 with bounded recursion.** Mechanisms evaluated left to right against the sender IP: `ip4` / `ip6` (CIDR match via the CIDR tool's parser), `include` (recurse into a pasted record for that domain, else "unresolvable — counted as a lookup, result unknown"), `a` / `mx` / `exists` / `ptr` (need DNS: counted as lookups and marked "needs DNS — paste the A/MX records to evaluate"), `redirect=`. The lookup counter follows §4.6.4 (10 limit; `ip4` / `ip6` / `all` do not count). The `exp=` modifier is shown, not expanded. Rejected alternative: refusing to evaluate without full recursion — a partial, honest answer is more useful than none.
8. **DMARC parser targets RFC 9989** and recognises the RFC 7489 tags: `pct`, `rf`, `ri` are shown with their old meaning and a "deprecated in RFC 9989 — receivers may ignore" ⚠; `np` (non-existent subdomain policy) and `psd` are explained; `t=y` (testing, the RFC 9989 replacement for `pct=0`) is recognised. Policy ladder `none` ⚠ → `quarantine` ✓ → `reject` ✓; `sp=` / `np=` weaker than `p=` is ⚠. Alignment uses mailhdr's organizational-domain approximation and says so. `rua` / `ruf` URIs are checked for `mailto:` syntax and a note explains the `_report._dmarc` external-destination verification record (RFC 9989 §7.1) when the report domain differs from the policy domain.
9. **ARC sets grouped by `i=`** (RFC 8617 §4): each instance has ARC-Authentication-Results, ARC-Message-Signature (verified exactly like DKIM over the message), and ARC-Seal (verified over the ARC header set of all instances ≤ i, in order, per §5.1.1). `cv=` on the highest seal gives the chain state; `cv=fail` or any seal failure makes the chain fail; the explanation says that ARC conveys the *forwarder's* authentication claim and that trusting it is the receiver's choice of which sealers to believe.
10. **DNS record linters are table-driven.** MTA-STS TXT (`v=STSv1; id=`) and policy file (`version`, `mode` enforce / testing / none, `mx` patterns, `max_age` with the RFC 8461 §3.2 recommendation of ≥ 604800 s); TLSRPT (`v=TLSRPTv1; rua=` mailto / https); BIMI (`v=BIMI1; l=` https SVG, `a=` VMC — "a certificate you can paste into the TLS Certificate Parser"); TLSA (usage 0–3, selector 0–1, matching 0–2 decoded with names, hex length check 32 / 64 for SHA-256 / 512); CAA (`flags` with the critical bit, tags `issue` / `issuewild` / `iodef` / `contactemail` / `contactphone` / `issuemail`, parameter syntax); DNSKEY (flags 256 ZSK / 257 KSK, protocol 3, algorithm names, key tag per RFC 4034 Appendix B — Appendix B.1 for algorithm 1) and DS (key tag, algorithm, digest type 1 / 2 / 4, digest length) with the match gate "DS key tag and algorithm match a pasted DNSKEY" and, for digest type 2, the digest recomputed with SHA-256 over owner name wire format ‖ RDATA.
11. **Primitives on the crypto axis**: RSA verify — Web Crypto; Ed25519 verify — Web Crypto with unavailable-fallback message; SHA-256 / SHA-512 for `bh=` and DS digests — Web Crypto; SHA-1 — never used (rsa-sha1 is reported as historic, not computed); DNSKEY key tag — pure JS 16-bit arithmetic; everything else is string parsing.

## Risks / Trade-offs

- **Pasted messages lose fidelity.** Copying from a mail client can change CRLF, trailing whitespace, or encoding; *simple* canonicalization is sensitive to all three. Mitigation: the tool normalises bare LF to CRLF, says which canonicalization was used, and suggests "Save as .eml / Show original" when `bh=` fails under `simple`; a file input accepting `.eml` bypasses clipboard mangling.
- **Key association mistakes.** A user may paste a key for the wrong selector. Mitigation: owner-name matching from `dig` output when present; otherwise the UI shows which key was used for which signature.
- **Bounded SPF recursion gives partial answers.** The result is labelled "evaluated with n of m includes expanded" and never "pass" when an unexpanded include could have matched before the terminal `all`.
- **DMARC organizational domain without a PSL.** `example.co.uk` vs `co.uk` mis-grouping is possible; mailhdr already carries this caveat and the panel repeats it.
- **Browser Ed25519 support.** Safari and Firefox ship Ed25519 in Web Crypto; older Chromium builds did not. Mitigation: capability check and an explicit "unavailable" state distinct from "fail".
- **False confidence.** A DKIM pass proves the signing domain signed these bytes; it says nothing about the content, the display name, or whether the signing domain is the one the user thinks. The verdict sentence from mailhdr stays, and the DMARC alignment row is what connects the signature to the visible `From`.
